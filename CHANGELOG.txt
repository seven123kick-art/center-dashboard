【発見の経緯】
  Dashboard/Indicators/Trend等の画面でDatasetが「未登録」と表示される
  不具合の調査（実機コンソールでの検証を含む複数ラウンドの調査）の結果、
  以下が確定した：
  - STATE.datasets.length（裸のSTATE） = 13（正しくデータが存在）
  - window.STATE = undefined
  - window.STATE === STATE → false
  - Repository.Dataset.getActive()内部は`window.STATE`を参照する設計の
    ため、window.STATEがundefinedである結果、早期returnで空配列[]を
    返していた

  原因：app.js内でSTATEは`const STATE = {...}`として宣言されており、
  `window.STATE = STATE`という明示的な代入がプロジェクト全体のどこにも
  存在しなかった。ブラウザのclassic script（type="module"でない
  <script>タグ）において、トップレベルのconst/let宣言は「スクリプト
  スコープ」に束縛されるが、windowオブジェクトのプロパティには自動的に
  ならない、というJavaScript／ブラウザ仕様の挙動が根本原因。

  影響範囲：DatasetRepository.getActive()に加え、window.STATEを参照する
  以下4ファイルの一部処理も同様の影響を受けていたことをコード確認済み：
  field_core.js（958行）、field_area.js（98,283,312,460,461,882,883,
  966,986行）、field_content.js（27行）、field_product.js（110,138,
  601,607行）。特にfield_area.js/field_product.jsの
  「if (window.STATE) { STATE.fiscalYear = ...; }」という形の条件分岐は、
  window.STATEが常にfalsyだったため、これらのブロックが一度も
  実行されていなかった（現場画面での年度・月選択保存が機能していな
  かった可能性）。

  他の主要オブジェクト（CONFIG/CSV/IMPORT/MODAL等）も同様に裸のconst
  宣言だが、window.CONFIG／window.CSV等という形で参照しているコードは
  プロジェクト全体でSTATE以外に存在しないことを確認済み（実害はSTATEの
  みに限定される）。STORE/CLOUD/AUTO_SYNC/NAV/UI/IDB_CACHEは、いずれも
  既に`var X = window.X = {...}`または`window.X = {...}`という正しい
  二重代入パターンで宣言されており、この問題の対象外であることも確認済み。

事前確認（今回のご指示に基づく安全確認）：
  実装前に、プロジェクト全体を以下の観点で検索し、いずれも該当なしを
  確認した：
  - window.STATE = への既存の代入：0件
  - delete window.STATE：0件
  - Object.defineProperty(window, 'STATE', ...)：0件
  - window['STATE'] 等の動的代入：0件
  他にwindow.STATEを書き換えるコードが存在しないことを確認した上で、
  1行のみを追加した。

修正内容：
  const STATE = { ... };
  window.STATE = STATE;  // ← 追加した1行（コメント除く）

  オブジェクト代入は参照渡しのため、この1行は「コピー」ではなく
  「同一オブジェクトへの別名付け」である。app.js内で今後も使われ続ける
  裸のSTATEへの書き込みは、そのままwindow.STATE側からも見える
  （Node.jsでの参照等価性テストにより確認済み）。
