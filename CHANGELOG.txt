【今回の追加対応（旧速報Cloud削除のタイミング修正）】

前回実装の成功パスは、全グループのローカル登録完了直後に
finalizeSupersedeDailyCloudDelete()（旧速報Cloudファイル削除）を
実行し、その後にSTATE.fiscalYear/selYM設定→Repository.Storage.save()
→SYNC_COORDINATOR.syncPush()（新データCloud保存）→_verifyCloudSaved()
（Cloud再取得検証）という順序になっていた。この順序では、
「速報Cloud削除は成功したが、新しい確定データのCloud保存に失敗する」
という中間状態が発生し得た。

■datasetKeyの衝突有無を確認した
CLOUD._datasetKey(ym, type)（src/core/cloud.js）の実装を確認した
結果、`${CENTER.id}/skdl/${ym}_${type}.json`という形式で、
type='daily'とtype='confirmed'は完全に異なるファイルパス
（例：202605_daily.json / 202605_confirmed.json）であることを
確認した。削除処理の実行タイミングを最後に回しても、新しい
確定データを誤って削除してしまうリスクはない。

■実行順序を要求通りに修正した
bulk_import.jsのhandleFiles()成功パスを、
  Phase1全件検証 → Phase2ローカル登録 → Storage保存 →
  Cloud新データ保存（syncPush） → Cloud再取得検証
  （_verifyCloudSaved） → 旧速報Cloud削除確定
  （finalizeSupersedeDailyCloudDelete） → 完了
という順序へ修正した。旧速報Cloud削除の実行位置を、Cloud保存・
検証が完了した後（try節の末尾、cloudSummary = 'クラウド一括保存: OK'
を設定する直前）へ移動した。
Cloud保存（syncPush）またはCloud再取得検証（_verifyCloudSaved）が
失敗した場合は、catch(e)節へ分岐し、旧速報Cloud削除の呼出し自体に
到達しないため、旧速報Cloudファイルには一切触れない
（削除しない）ことを保証した。

■finalizeSupersedeDailyCloudDelete()の削除成否検知を追加した
既存のfinalizeSupersedeDailyCloudDelete(ym)は、内部でIDB_CACHE.remove/
CLOUD_REPOSITORY.deleteFileの失敗をtry/catchで握りつぶしており、
呼出元が成否を検知できなかった。
opt.throwOnErrorという新規オプションを追加し、trueの場合のみ
削除失敗時に例外を投げるようにした。opt省略時（個別通常取込、
supersedeDailyWithConfirmedのデフォルト呼出）は、従来通りエラーを
握りつぶすだけで例外を投げない（diff確認済み、呼出箇所
`await finalizeSupersedeDailyCloudDelete(ym);`は引数を一切
変更していない）。
bulk_import.js側は、finalizeSupersedeDailyCloudDelete(ym,
{ throwOnError: true })という形で削除失敗を検知し、
deleteFailures配列へ蓄積してcloudSummaryメッセージへ反映する
（データ自体は正しく登録されているため、致命的エラーとはせず、
「クラウド一括保存: OK」に付随する警告として表示する設計とした）。

■① IMPORT.processCSV()にstrictモードを追加した
bulk_import.jsのPL登録が呼んでいたIMPORT.processCSV()は、内部で
各ファイルをtry/catchし、失敗してもthrowせず処理を継続していた。
また呼出元のMath.max(g.files.length, after-before, 1)により、
実登録に失敗していても成功件数として扱われる可能性があった。

app.js側のprocessCSV(files, ym, opt={})に、opt.strictという新規
オプションを追加した。strict時のみ：
  ・1ファイルでも解析/登録失敗（parseSKDLがnullを返す、または例外）
    → strictFailures配列へ蓄積し、ループ完了後にthrow
  ・imported件数0、または imported !== files.length
    → throw
  ・一部成功していても、この関数はThrowによって呼出元へ失敗を
    確実に伝播する（bulk_import.js側のcatchへ必ず到達する）
opt.strict省略時（個別通常取込）の挙動は完全に維持した：
  ・失敗ファイルはUI.toastで警告表示するだけで処理を継続
  ・imported>0であれば「一部成功」として登録を確定し、
    NAV.refresh()/UI.toast(成功)/UI.updateSaveStatus()を実行
  （diff確認済み、既存の分岐は1つも削除・変更していない。
  strict用の追加ロジックは全て「if (opt.strict)」で完全に
  ガードされた新規コードのみ）

bulk_import.js側は、
  await IMPORT.processCSV(g.files, g.ym, { replace:true, awaitCloud:false, strict:true });
という形でstrict:trueを渡し、戻り値（実際に登録された件数）を
そのままcountとして使うよう修正した。従来の
Math.max(g.files.length, after-before, 1)という「成功件数の捏造」
は完全に削除した。
_importPLGroup()（IMPORT.processCSVが存在しない場合のフォールバック
経路）は、元々各ファイルの解析失敗時に即座にthrowする実装で
あったため、この点は既に安全だった。この経路にも②のCloud削除
延期オプションのみ追加した（imported件数の扱いは元から捏造して
いなかったため変更していない）。

■② supersedeDailyWithConfirmed()のCloud即時削除を一括取込中だけ延期した
既存のsupersedeDailyWithConfirmed(ym)は、STATE変更
（markDataDeletedによるtombstone記録＋STATE.datasetsからの除外）
に加えて、CLOUD_REPOSITORY.deleteFile()によるCloud側への即時
削除リクエストを実行していた。これは後続グループが失敗して
STATEをロールバックしても元に戻せない不可逆な副作用だった。

【調査結果（正直な報告）】
ご指示にあった「tombstone/STATE.deleted/syncPush側で既に安全に
削除を反映できる仕組み」を実コードで確認した結果、
SYNC_COORDINATOR.syncPush()は「現在のSTATE.datasetsの内容を
Cloudへアップロードするだけ」の実装であり、STATE.datasetsから
除外されたデータセットに対応する既存のCloudファイルを能動的に
削除する仕組みではないことが判明した。STATE.deletedのtombstone
（markDataDeleted）は、Pull（他端末からの取得）時に「このデータは
削除済みなので復元しない」という目的でのみ使われており（
sync_coordinator.js内のisDeletedSince呼出箇所で確認）、Push側で
Cloud上の実ファイルを能動的に削除するトリガーにはなっていない。
このため、「既存の安全な削除反映の仕組みをそのまま再利用する」
という当初の想定通りの対応はできず、代わりに以下の最小限の
方法を選んだ。

【実装内容】
supersedeDailyWithConfirmed(ym)を、
  ・STATE変更（tombstone記録＋datasets配列からの除外）を行う本体
  ・実際のCloud削除（IDB_CACHE.remove／CLOUD_REPOSITORY.deleteFile）
    を行うfinalizeSupersedeDailyCloudDelete(ym)という新規の分離関数
の2つへ分割した。新しい削除方式は作らず、既存のCloud削除呼出し
（IDB_CACHE.remove/CLOUD_REPOSITORY.deleteFile、コード自体は
1文字も変更していない）を、実行するタイミングだけ分離しただけで
ある。
supersedeDailyWithConfirmed(ym, opt={})にopt.deferCloudDeleteを
追加し、
  ・opt省略時（デフォルト、個別通常取込）：STATE変更の直後に
    finalizeSupersedeDailyCloudDelete(ym)を即座に呼ぶ。これは
    従来と完全に同じシーケンスであり、個別通常取込の動作は
    一切変更していない（diff確認済み）。
  ・opt.deferCloudDelete===true（bulk_import.jsのみ使用）：
    STATE変更は即座に行うが、Cloud削除は実行せず
    {deferred:true, ym}を返す。
bulk_import.js側は、pl種別グループの登録が確定型で、かつ登録前に
速報データが存在した場合、そのymをpendingSupersedeDailyYmsという
ローカル配列（STATE構造への追加ではない、bulk_import.js内の
一時変数）へ記録する。全グループの登録処理が成功した場合のみ
（bulkFailedチェックを通過した後）、pendingSupersedeDailyYmsに
記録された各ymについてfinalizeSupersedeDailyCloudDelete(ym)を
呼び、初めてCloud側の削除を確定させる。ロールバック時
（bulkFailed）はこのブロックへ到達しないため、Cloud側の削除は
一切実行されない。

前回セッションまでの内容（参考、今回変更なし）

前回実装のPhase 2は、各グループを「try→登録→catchでNGログ→次group
へ」と処理する構造であり、group Aの登録が成功した後にgroup Bの
登録処理で予期しない例外が発生すると、group AのSTATE変更が残った
状態で最後のRepository.Storage.save()まで到達する可能性があった。
今回、Phase 2直前にSTATEスナップショットを取得し、1グループでも
登録処理が失敗した場合は即座に処理を中止してロールバックする
構造へ修正した。

■スナップショット対象の特定
今回の一括取込（pl/worker/product）で変更され得るSTATEのプロパティを、
upsertDataset()（app.js）・upsertByYm()（field_core.js）・
clearDataDeleted()（app.js）の実装から特定した：
  ・STATE.datasets（pl取込、upsertDatasetで配列を再構築）
  ・STATE.workerCsvData（worker取込、upsertByYmで配列を再構築）
  ・STATE.productAddressData（product取込、同上）
  ・STATE.deleted（pl/worker/product共通、clearDataDeletedで
    {kind:{key:timestamp文字列}}という単純なJSON互換構造を変更）
  ・STATE.fiscalYear / STATE.selYM（pl成功時にhandleFiles末尾で設定）
STATE全体を雑にJSONコピーして差し替えることは行っていない
（既存参照や非JSON値を壊すリスクを避けるため）。上記5プロパティ
だけを対象に、配列は浅いコピー（スプレッド構文）、STATE.deleted
はJSON深いコピー（プレーンなJSON互換構造のため安全）で退避した。
STATEオブジェクトそのものの参照は一切変更していない
（STATE.datasets = ... のようにプロパティへ代入するのみで、
STATE = {...} のような参照の差し替えは行っていない）。

■ロールバック手順
Phase 2のグループ処理ループのcatch節を、「NGログを残して次の
グループへ進む」から「NGログを残して即座にループをbreakする」へ
変更した（catchしてNGログだけ残し次のgroupへ進む挙動は廃止した）。
ループ脱出後、bulkFailedフラグが立っていれば：
  1. STATE.datasets/workerCsvData/productAddressData/deleted/
     fiscalYear/selYMを、Phase 2直前のスナップショットへ復元
  2. FIELD_DATA_ACCESS.invalidate()でキャッシュを整合させる
  3. Repository.Storage.save()でロールバック後の状態をローカルへ
     保存する
  4. AUTO_SYNC.resume()で抑制を解除する
  5. 「一括取込に失敗したため、今回の登録内容はすべて取り消しました。
     原因：○○」というメッセージを表示する
  6. return文でCloud pushAllのブロックには一切進まない
というロールバック処理を行う。CLOUD.pushMonthの一時抑制解除は
既存のtry/finally構造（ループの成功・失敗を問わず必ず実行される）
をそのまま利用しており、今回変更していない。

■既知の制約（正直な報告）
pl（確定区分）の登録処理には、既存のsupersedeDailyWithConfirmed()

Cloud側の副作用は、今回のロールバック実装の対象（STATEの復元）

■① bulk_import.jsを本当のall-or-nothingにした
前回実装では、年月判定不能・CSV種別unknown・グループ取込失敗の
いずれも「スキップ／catchして次へ」という設計であり、異常CSVと
正常CSVを混在させると正常側だけ登録されてしまう問題が残っていた。

既存parser（CSV.parseSKDL/parseWorkerCsvRows/
parseProductAddressRows/assertNotForeignCsv/assertOwnCsvSignature）
は一切変更せず、handleFiles()の内部構造を以下の2段階へ明確に
分離した：

Phase 1（全ファイル事前検証、STATE/Storage/Cloudへは一切書き込まない）
  ・全ファイルの年月判定（_ymFromName、既存関数そのまま）
  ・全ファイルのCSV種別判定（_classify、既存関数そのまま）
  ・種別ごとのグループ化後、各グループについて既存parser/
    validationを「検証だけ」実行する：
    - plグループ：CSV.read()+CSV.parseSKDL()を呼び、
      戻り値がfalsyならエラー（_importPLGroupと同じ判定基準）
    - workerグループ：新規追加のvalidateWorkerCsvFilesOnly()
      （field_core.js）が、既存のassertNotForeignCsv/
      assertOwnCsvSignature/parseWorkerCsvRowsをそのまま呼び出す
    - productグループ：同様にvalidateProductCsvFilesOnly()
      （field_core.js）

③ 誤取込防止方法
============================================================
detectForeignCsvSignature(rows, sampleText, ownType)
（field_core.js、新規）:
  ヘッダー行に「エスライン原票番号」「お届け先郵便番号」が
  あれば商品・住所CSV、「作業者名」「担当者」「配送担当」が
  あれば作業者別CSV、本文に"SKDL0001/0003"の記載または先頭列が
  「科目」であれば収支CSV(SKDL)と判定し、取込先（ownType）と
  異なる強いマーカーが検出された場合のみ拒否する。
  意図的に「取込先自身の形式であることの積極確認」は要求せず、
  「他形式である強い根拠がある場合のみ拒否」という一方向の
  チェックにした。これは、ヘッダー表記の揺れで既存の正常な
  ファイルまで誤って拒否してしまう回帰リスクを避けるための
  安全側の設計判断である。
  実際に5パターン（作業者→商品/商品→作業者/SKDL誤投入/正常な
  作業者CSV/正常な商品CSV）でテストし、誤操作系は拒否・正常系は
  通過することを確認した。

  ガード呼び出しはimportWorker/importProductの**ファイルループの
  先頭**に配置しており、STATE/upsertByYm/Repository.Storage.save()
  等の実際の永続化処理はループ完了後にまとめて行われる既存構造の
  ため、ガードで例外が投げられた時点では一切のデータ書き込みが
  発生していないことを確認済み（登録前に確実に停止する）。

【追加対応（ユーザー指摘への修正）】
  上記のassertNotForeignCsv()は「他形式である強い根拠がある場合の
  み拒否する」negative validationであり、作業者別・商品住所・
  SKDLのいずれにも該当しない無関係CSVが素通りしてしまう問題が
  残っていた。既存parserのheaderIndex(...,fallback)/findIdx(...,
  fallback)が、ヘッダーが見つからない場合に固定列位置へ
  フォールバックするため、「parserがエラーなく読めたこと」を
  ファイル形式の証明にできない（無関係CSVでも1列目や8列目等を
  それらしく解釈して処理を通過してしまう）ことを確認した。

  これに対応するため、取込先自身の形式が実際に成立していることを
  確認するpositive validationを新規追加した：

  validateWorkerCsvSignature(rows, fileName)
    parseWorkerCsvRowsと同じ候補ヘッダー名（作業者名／作業者／
    担当者／社員名／氏名）で作業者名列を探すが、ヘッダー名で
    見つからない場合（フォールバックで0列目に頼る場合）は
    不合格とする。作業者別CSVは、商品・住所CSVのように固定列
    位置での取込がUI上正式に案内された前例が既存コード上に
    存在しないため、ヘッダー名一致を必須要件とした。
    加えて、本文サンプル（最大30行）のうち、作業者名列の値が
    数字のみでない割合（氏名らしさ）と、日付列の値が
    normalizeWorkDate()で正しく解析できる割合を、それぞれ60%以上
    要求する。

  validateProductCsvSignature(rows, fileName)
    商品・住所CSVは、center.html上のUI案内文自体に「I列
    エスライン原票番号」「R列作業内容」「U列金額」という具体的な
    列位置（インデックス8/17/20）が明記されており、固定列位置での
    取込が正式に許容された形式であることが既存コードから確認できた
    （想像で決めていない）。そのため、ヘッダー名の有無に関わらず、
    本文サンプル（最大30行）における値パターンで実データ性を
    複数の観点から確認する：
      ・郵便番号列（フォールバック11列目）：normalizeZip()適用後に
        ちょうど7桁（日本の郵便番号形式）になる割合が50%以上
        であることを必須とする
      ・原票番号列（フォールバック8列目）：normalizeSlipNo()適用後
        6文字以上になる割合、または金額列（フォールバック20列目）：
        yen()で数値として解釈できる割合、のいずれかが50%以上
    郵便番号（7桁という明確な形式的特徴）を必須とし、残り2指標の
    いずれかとの組合せを要求することで、複数の列位置・値パターンを
    同時に確認する設計にした。

  基本フローは、
    拡張子確認（既存accept属性＋ファイル選択時のフィルタ）
    → 他形式検出（assertNotForeignCsv、既存のnegative validation）
    → 対象形式positive validation（assertOwnCsvSignature、今回追加）
    → parser（parseWorkerCsvRows/parseProductAddressRows、無変更）
    → 登録（STATEへの書込・Repository.Storage.save()、無変更）
  の順に統一した。positive validationに失敗した場合は
  「${fileName}：このファイルを「${targetLabel}」として確認できません
  （${reason}）。登録は行っていません。」という形式でエラーを投げ、
  呼出元の既存catch節（msg()でのエラー表示）がそのまま処理する。

============================================================
⑦ 6月PDFノイズの根本原因
============================================================
route_analysis.jsのparsePageText()内、作業者名抽出の正規表現：
  /作業者\s*[:：]?\s*(.+?)(?=\s+配達持出リスト|\s+作業者TEL|\s+支店|$)/
という終端条件（lookahead）に、PDFページのフッター相当
（印刷日時・"Page n/n"）が含まれていなかった。
一部のページレイアウトでは、pdfTextLines()のy座標グルーピング
（許容誤差±3.2）により、「作業者」ラベルを含む行に印刷日時や
ページ番号が同一の視覚行として結合されることがあり、既存の
終端条件（配達持出リスト／作業者TEL／支店）がその行内に存在
しないと、非貪欲マッチが行末（$）まで一気に伸び、フッター文字列
ごと作業者名として抽出されていた。これが実例の
「北さいたまセンター 2026/07/23 14:29:47 Page 1/4」
「武村 知 2026/07/23 14:29:47 Page 1/3」
の直接原因である。

============================================================
⑧ その修正方法
============================================================
1. 終端条件（lookahead）に印刷日時パターン・"Page n/n"パターンを
   追加し、フッターが同一行に来ても正しくそこで止まるようにした。
2. 上記1でも取り切れない場合の保険として、抽出後に印刷日時・
   "Page n/n"パターンを末尾から除去するクリーンアップ処理を追加。
3. クリーンアップ後も「○○センター」のみ（実際の氏名を伴わない）
   が残った場合は、実データを推測で確定させず、作業者名は

最終報告（今回追加分・ご指摘への回答）

1. 各CSVを「正しい形式」と判定する具体的条件
   作業者別CSV：
     ・ヘッダー行に「作業者名／作業者／担当者／社員名／氏名」の
       いずれかが存在すること（フォールバック列位置での代用は
       不合格とする）
     ・本文サンプル（最大30行）中、作業者名列の値が数字のみでない
       割合が60%以上
     ・本文サンプル中、日付列（ヘッダー一致があればその列、なければ
       0列目）の値がnormalizeWorkDate()で解析できる割合が60%以上
   商品・住所CSV：
     ・郵便番号列（ヘッダー一致があればその列、なければ11列目＝
       center.html案内文にあるL列）の値がnormalizeZip()適用後に
       ちょうど7桁になる割合が50%以上（必須）
     ・かつ、原票番号列（8列目＝I列）がnormalizeSlipNo()適用後
       6文字以上になる割合、または金額列（20列目＝U列）がyen()で
       数値解釈できる割合の、いずれかが50%以上

2. 不明CSVが登録されないこと
   assertOwnCsvSignature()が上記1の条件を満たさないと判断した
   場合、ErrorをthrowしてimportWorker/importProduct関数の実行を
   その場で中断する。呼出元（FIELD_WORKER_IMPORT2.handleFiles等）
   は既存のcatch節でエラーメッセージを表示するのみで、STATE・
   Repository・Cloudへの書込処理には一切到達しない。

3. parser実行前にvalidationが完了すること
   importWorker/importProductのファイルループ内で、
   ①assertNotForeignCsv()（他形式でないことの確認）
   ②assertOwnCsvSignature()（対象形式として成立することの確認）
   の両方を、parseWorkerCsvRows()/parseProductAddressRows()の
   呼出より**前**に実行する構成にした（コード上、同一ループ内で
   validation呼出の直後にparser呼出が続く形で確認済み）。

4. STATEへの書込前に全validationが完了すること
   importWorker/importProductとも、ファイル単位のvalidation・
   parse処理は全てメモリ上の一時変数（combined/allTickets等）への
   集計にとどまり、STATE.workerCsvData/STATE.productAddressDataへの
   実際の書込（upsertByYm呼出）およびRepository.Storage.save()は、
   全ファイルのループが正常に完了した**後**にのみ実行される既存
   構造をそのまま利用した。したがって、いずれか1ファイルでも
   validationに失敗すると、その時点で例外により関数全体が中断され、
   STATEへの書込は一切発生しない。
