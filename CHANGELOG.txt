Version6 D4-39: ホーム画面荷主分析 Canonical Read Model優先移行
（2026-08-18、投入前レビュー指摘の修正反映）

【投入前レビューで発見された問題と修正】
基準SHA 1610cde19d552d01d78bf795752569db78aa1a26 に対する
D4-39実装（初版）のZIPをレビューした結果、
resolveShipperGroupsForYM(ym)のNOT_LOADED判定に問題が指摘された。

既存のCANONICAL_ANALYSIS_READ_MODELS.loadMonth()は、
WORKER_SALES CURRENTだけ存在しSHIPPER_AREA CURRENTが存在しない
月でも、status:'READY', worker:非null, shipper:null を返す既存
仕様がある。初版の判定ロジックはこのケース（READYだがshipperが
null）を「READY+shipperあり」にも「LEGACY_FALLBACK」にも
一致させられず、デフォルトのNOT_LOADED分岐に落ちていた。その
結果、ホーム荷主表示で
  READY+shipperなし → NOT_LOADED → loadMonth() →
  キャッシュ済みREADY（内容は変わらない） → 再度NOT_LOADED
という再ロード・再描画ループが発生し得る状態だった。

【修正内容】
resolveShipperGroupsForYM(ym)の判定順序を、
  1. peek(ym) が null／undefined（真のキャッシュミス）
     → NOT_LOADED（loadMonth()を実行すべき唯一のケース）
  2. status==='READY' && shipperが存在
     → READY（Canonical、shipper.groupsのみ使用）
  3. status==='READY' && shipperが存在しない
     （その月にSHIPPER_AREA CURRENTが存在しない）
     → LEGACY_FALLBACK
  4. status==='LEGACY_FALLBACK'
     → LEGACY_FALLBACK
  5. Canonical基盤自体が利用不能
     → UNAVAILABLE（呼出元でLEGACY_FALLBACKと同様に扱われる）
という順序へ修正した。peek(ym)が非null（READYでも
LEGACY_FALLBACKでも）で返ってきた時点で、必ずどちらかへ即座に
確定させ、それ以上loadMonth()を呼び直さないようにした。
新しい状態（state値）や新しい集計ロジックは追加せず、既存の
判定ルールの修正のみを行った。
