②現在のみなし人件費率の計算式
============================================================
src/app.js processDataset()（既存、今回一切変更していない、バイト
単位で完全一致を確認済み）：
  分子（laborCost）= 人件費（給与手当+人材派遣料+その他人件費）
    + 傭車費（路線傭車+路線備車+集配傭車+社内外注費、"委託費"を除く）
  分母（pseudoLaborIncome）= max(0, 営業収益 − 委託収入)
  pseudoLaborRate = 分母>0 ? 分子/分母*100 : 0
既存コードのコメントに「委託取引を分子・分母の双方から除外する」と
明記されている通り、現在の「みなし人件費率」は実質的に
「委託除外ベース」の定義そのものだった。

============================================================
③委託除外ベースの計算式
============================================================
②の既存pseudoLaborRateをそのまま「委託除外」として使用した
（新規計算ロジックの追加なし）。

【総額ベース（今回新規算出）】
分子（totalLaborCostFull）= ds.laborCost + ds.excludedConsignmentExpense
  = 人件費 + 傭車費(委託費除く) + 委託費
  = 人件費 + 傭車費全額（CONFIG.YOSHA_KEYS全体を含む）
分母 = ds.totalIncome（委託収入を除外しない営業収益そのまま）
pseudoLaborRateFull = totalIncome>0 ? totalLaborCostFull/totalIncome*100 : 0

新たな科目再集計（CONFIG.XXX_KEYS.reduce等）は一切行わず、
processDataset()が既に計算済みのdsプロパティ（laborCost/
excludedConsignmentExpense/totalIncome）の単純な足し算・割り算のみ
で算出した。委託収入="委託収入"科目（CONFIG.INCOME_KEYS内）、
委託費="委託費"科目（CONFIG.YOSHA_KEYS内）という既存科目区分を
そのまま踏襲しており、対応関係の一意性・正確性は既存の
processDataset()の設計に依拠している。

⑦赤字時の比較表示ルール
============================================================
homeCompareInfo(current, compare, isExpense, sameLabel)：
  compare > 0：既存ratio()をそのまま使用（通常ケース、完全無変更）
  compare === 0：'—'
  compare < 0 かつ current > 0：'黒字転換'
  compare < 0 かつ current === 0：'黒字化'
  compare < 0 かつ current === compare：sameLabel（前月比なら
    '前月並み'、前年比なら'前年並み'）
  compare < 0 かつ current > compare：'赤字縮小'
  compare < 0 かつ current < compare：'赤字拡大'
色判定（pill up/down）は、isExpense=falseなら「差額>0→up(緑)」、
isExpense=trueなら「差額<0→up(緑)」という既存画面
（予実差異分析等）と同じ考え方で統一した。

⑧80.0%超過問題の原因と修正内容
============================================================
【原因】共通fmt(v,d)（src/core/format.js、今回一切変更していない）
は、実際にはMath.round(v)で先に整数へ丸めてから
Intl.NumberFormatでフォーマットしており、d（小数桁数指定）は
「常に整数丸め」という実質的な挙動になっている（例：80.04→
Math.round→80→"80.0%"と表示）。一方、既存の判定ロジックは
ds.pseudoLaborRate（丸めていない生値）と閾値80を直接比較していた
ため、生値が80.04〜80.49の範囲では「80.0%」と表示されながら
「超過」と判定される矛盾が生じていた。

【修正内容】共通fmt()/pct()自体は他画面（月次収支等）へ影響する
ため変更せず、ホーム画面側だけで表示に使われているのと同じ丸め
処理（Math.round、整数丸め）を判定にも適用した：
  pseudoLaborRateRounded = Math.round(ds.pseudoLaborRate)
  pseudoLaborAchieved = pseudoLaborRateRounded <= CONFIG.TARGETS.pseudoLaborRate
これにより、表示される数値と達成/超過の判定が常に整合するように
なった（境界値テストで確認済み、⑨参照）。単純に閾値を緩めたのでは
なく、既存の丸めルールに判定を合わせる形で整合させた。
